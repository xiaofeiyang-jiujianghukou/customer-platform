## 一、项目背景与目标

### 1.1 背景

在现有CRM系统中，客户资源查询存在以下痛点：
- MySQL复杂查询响应慢（4s+）
- 多条件组合查询效率低
- 高频查询场景对主库压力大
- 缺乏可视化的客户管理界面

### 1.2 目标

构建一套高可用的客户数据同步平台，实现：
- MySQL到ES的实时数据同步（毫秒级延迟）
- 多条件组合查询响应时间降至200ms以内
- 读写分离：MySQL处理写入，ES处理查询
- 服务解耦：各服务独立部署、独立演进
- 提供Web界面进行客户资源管理（查询、详情、编辑、批量生成测试数据）

- **40% 更新**（400条）：随机选取已存在的有效客户，更新 name/phone 等字段
- **20% 逻辑删除**（200条）：随机选取已存在的有效客户，status 置为 1

注意：更新和删除操作在新增之前先查询已有数据，确保只操作存量数据。

### 3.2 ES同步服务 (es-sync-service)

#### 3.2.1 职责
- 消费RocketMQ消息（仅包含客户编号+事件类型）
- 根据客户编号从MySQL读取全量客户数据
- **按 status 分类处理**：status=0 → upsert到ES，status=1 → 从ES删除
- 暴露分页查询接口（仅返回客户编号）

#### 3.2.2 核心接口

| 方法 | 路径 | 描述 |
|------|------|------|
| POST | /internal/es/page | 多条件组合分页查询（仅返回客户编号） |
| GET | /internal/es/health | 健康检查 |

#### 3.2.3 逻辑删除处理

关键设计变更：MySQL 逻辑删除（`UPDATE status=1`）被 Canal 识别为 UPDATE 事件，ES 同步服务在读到 MySQL 全量数据后，检查 `status` 字段：
- `status=1` → ES 执行 `delete`（物理删除文档）
- `status=0` → ES 执行 `update(docAsUpsert)`（覆盖写入，文档 `_id` = `customerNo`）

这保证了 ES 只包含有效记录，ES 文档数与 MySQL 有效记录数一致。

#### 3.2.4 ES写入策略

使用 ES 8.11 Java Client 的 Bulk API，`_id` 设为 `customerNo`：
- 新增/更新：`update` + `docAsUpsert(true)` — 按 `_id` 覆盖，零重复
- 逻辑删除：`delete` — 按 `_id` 物理删除

### 3.3 Canal同步服务 (canal-sync-service)

#### 3.3.1 职责
- 监听MySQL binlog（通过Canal Server）
- 所有 INSERT/UPDATE/DELETE 事件全量收集
- 批量窗口内按 customer_no 去重（同一窗口内后覆盖前）
- 发送变更消息到RocketMQ（仅含客户编号+事件类型）

#### 3.3.2 批量收集策略

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 批量大小（size） | 162 | 1000ms窗口收集约150-170条，162在4:6临界线 |
| 时间窗口（intervalMs） | 1000ms | 1秒 |
| 去重窗口 | 与时间窗口同步 | 窗口内同customer_no后覆盖前 |

**策略设计思路**：
- canal 每批交付~6条binlog事件（约40ms/批）
- 1秒窗口内可收集约150-170条（去重后）
- 设size=162：高频时（>162条/秒）COUNT先触发（~940-990ms），降速时（<162条/秒）TIME先到期（1000ms）
- 经压测验证，触发比例稳定在 **COUNT 40% : TIME 60%**（4:6开），自然交替

**压测数据**：
```
累计批次数: 30
FLUSH-COUNT: 12 (40%)  avg触发窗口: 961ms
FLUSH-TIME:  18 (60%)  avg未达标收集: 149条
FLUSH-FORCE: 5  (尾部兜底)
```

**环境变量可调**：`SYNC_BATCH_SIZE` 和 `SYNC_BATCH_INTERVAL_MS`，无需重新编译。

#### 3.3.3 窗口重置规则

无论哪种触发方式（COUNT / TIME / FORCE），flush 后都会重置：
- `customerEventMap` 清空
- `windowStartTime` 更新为当前时间
- `rawEventsInWindow` 归零

**特别修复**：空闲期间 `flush()` 即使 map 为空也重置窗口，防止长时间空闲后窗口膨胀（如 8000+ms）导致单条事件就触发 FLUSH-TIME。

#### 3.3.4 消息格式

```json
{
    "changes": [
        {"customerNo": "VA000000001", "eventType": "UPDATE"},
        {"customerNo": "VA000000002", "eventType": "INSERT"}
    ],
    "timestamp": 1700000000000
}
```

## 七、数据一致性保障

### 7.1 同步链路

```
MySQL变更 → Canal(at-least-once) → canal-sync-service(批量去重) → RocketMQ → es-sync-service(读MySQL) → ES(upsert/delete)
```

### 7.2 幂等设计

- ES写入使用 `customerNo` 作为文档 `_id`，upsert 天然幂等
- Canal侧同一客户在时间窗口内的多次更新自动去重合并（后覆盖前）
- ES逻辑删除处理：`status=1` 的行从 MySQL 读到后，直接从 ES 物理删除

### 7.3 验证结果

经多次全链路压测验证（MySQL写入 → Canal → MQ → ES同步 → 前端查询）：

| 指标 | 结果 |
|------|------|

### 9.1 Bug修复

| 问题 | 根因 | 修复 |
|------|------|------|
| generateTestData 空表仍显示 updated=400 | 先插后查，刚插入的记录也被更新/删除 | 改为先查已有数据再执行新增 |
| Collections.shuffle 抛 UnsupportedOperationException | Stream.toList() 返回不可变列表 | 包装为 new ArrayList<>() |
| ES有200条重复文档 | 逻辑删除(UPDATE status=1)在ES侧仍走upsert | es-sync-service 检查status，status=1 改为delete |
| canal FLUSH全部为TIME触发 | application.yml size=400远大于1000ms收集量 | size改为162，与1000ms窗口收集量匹配 |
| 空闲后窗口膨胀至8000+ms | flush()空时未重置窗口 | 空时也重置 windowStartTime |
